# Task Lifecycle (orchestrated build → review → fix → verify → report)

**Core:** The main session coordinates; ALL substantive work happens in subagents. The user reviews the final package (diff + evidence + open items), not the process. Every loop has a hard cap.

**Announce at start:** "I'm using the task-lifecycle skill."

---

## Pipeline overview

```
INPUT: spec / issue / user request
  │
  ├─ 0. Intake: classify size, pick branch strategy
  ├─ 1. BUILD        — builder subagent(s)          [via executingplans for planned work]
  ├─ 2. REVIEW LOOP  — code-reviewer subagent
  │       findings CRITICAL/HIGH/MEDIUM → builder subagent fixes → re-review
  │       repeat ≤ 3×; LOW / uncertain → collect for report, do NOT auto-fix
  ├─ 3. SECURITY     — backend-security-coder subagent (only if triggers match)
  ├─ 4. VERIFY       — verify-e2e skill in a FRESH subagent
  │       FAIL → fix via builder → re-verify (≤ 3×); BLOCKED → record gap, report
  └─ 5. REPORT       — one package: what/why, review iterations, evidence, open items
OUTPUT: verified change on a branch + evidence — user decides merge/push/deploy
```

---

## Step 0: Intake

1. Restate the task in 1-2 sentences; if the spec is ambiguous on something that changes the implementation, ask now — never mid-pipeline.
2. Classify size:
   - **Trivial** (copy, CSS, config, docs; **also a test-only diff ≤ 10 lines whose proof is a one-command mutation probe** — a new latch entry, a fixture row, a deleted tautological assertion) — skip to Step 1, DIRECT edit allowed (per `executingplans` DIRECT rules), then jump to Step 4. For the test-only case the DIRECT edit is legitimate ONLY with the mutation probe run and its RED/GREEN line quoted in the report; without the probe it is a Small task. MEASURED (KonkretnyTMS batch 2.3): a 2-line latch addition done inline with the probe cost ~2k tokens; the same work through a builder subagent costs a 40k spawn minimum.
   - **Small** (single coherent fix, expected diff < 30 lines, ≤ 2 files, NOT touching money/VAT, auth/permissions, or regulated data) — one builder subagent, then ONE review pass (no loop; findings fixed once, no re-review unless CRITICAL). Skip Step 3. Step 4 only if a user-facing surface changed. This class exists to stop 8-line fixes from paying the full-pipeline cost. **Small has a builder call budget of ~50 tool calls**, stated in the brief; a "does this defect class occur elsewhere" sweep is NOT the builder's job — it is either a separate `Explore` brief (`model: sonnet`, ≤ 20 calls, report the hits only) or the brief says "one grep, report the hits, do not dig". `POMIAR` (batch 3.1, #685): a Small builder (one model line + tests) made 83 calls / 22.9M input, ~40% of them measuring `AUTO_INCREMENT` on 8 tables and reading a controller — two valid spin-off issues, produced in the most expensive context available. **The Small review pass is NARROW:** the brief carries the diff stat plus 3–4 two-sided questions specific to the change ("does X hold or not-X — what decides it"), `code-reviewer` on opus, tier S on its side, expected ≤ 15 calls. `POMIAR` (batch 3.1): narrow review of #685 cost 2.6M / 11 calls and still produced a valid P3 outside the diff; a full review of a Standard diff in the same batch cost 11.8M. Sensitive modules are excluded by the class definition, so the narrow form never meets them. If the project's own review threshold (CLAUDE.md) exempts a diff of this size outside sensitive modules from the reviewer agent, the builder's self-audit checklist replaces the review pass — the project rule wins over this generic one. **Small tasks whose diff is test-only, or whose production diff is ≤ 10 lines outside sensitive modules, skip Step 4 entirely:** the builder's self-audit plus the targeted run IS the verification, and a fresh verifier would re-derive the same two commands for a 30k spawn. Step 4 stays mandatory the moment a user-facing surface changes.
   - **Standard** (single feature/bugfix, one coherent change) — Step 1 with one builder subagent.
   - **Large** (multi-task, 3+ modules, needs design — or the project's own decision tree routes it to a written plan, e.g. more than 3 implementation steps, a regulated/financial domain) — route through `brainstorming` → `writingplans` → `executingplans` for the build; this skill then owns Steps 2-5 on the combined result.
3. **Task context block (mandatory for Standard/Large):** at intake write a short context block — target files, canonical paths/services for any variant work, decisions already made, hard constraints ("do NOT touch X"). Paste it into EVERY subagent prompt in this lifecycle. Before each review iteration, append the previous iteration's findings + what was changed — reviewer N must know what reviewer N-1 found. Subagents rediscovering the project from scratch is both the main token cost and a source of contradictory decisions. Every number and fact in the block — and in every later brief — comes from a command executed in this turn, quoted next to it, never from memory or an earlier turn; a false number in a brief is an anchor the subagent pays to unlearn (`POMIAR` batch 3.1: three such false alarms, see `roadmapa` §3).
4. **Branch strategy:** if the project deploys from its main branch (deploy gate on push), create a feature branch first — `agent/<slug>` or `agent/issue-<n>`. Autonomous work must never have a direct path to production. Merge/push to main is ALWAYS the user's decision. If this lifecycle runs outside the main tree (the roadmapa queue's worktree, or any parallel work), it runs in its OWN worktree — a branch cannot share a working tree with another branch — and every command in every subagent prompt uses absolute paths under that worktree (the session cwd stays in the main tree). Apply the project's worktree checklist (missing `.env`, build flags, `node_modules`, tool binaries) before the first test run — a worktree without it produces a false baseline.

## Step 1: Build (in a subagent)

- Select the builder per the `executingplans` agent table (php-pro / javascript-pro / sql-pro / backend-security-coder / ...). When unsure → specialist agent, not DIRECT.
- **A brief spanning more than one layer (SQL migration + PHP service + JS front) is split into narrow builders per layer** — sequential when they depend on each other (migration first, its report is the second builder's input), parallel when file-disjoint — each with a stated budget of ≤ ~60 tool calls. Every tool call re-reads the builder's whole context, so cost grows with the square of the call count on one growing context; two half-size contexts are cheaper than one. `POMIAR` (batch 3.1, #687): one builder across three layers and three kinds of tests — 124 calls, 40.4M input, 2.7× the cost of a comparable single-layer builder at the same context size (#685: 83 calls, 22.9M).
- **A Standard/Large builder brief orders the work write-first, and a builder has no self-assessed context budget.** The brief says, as text: "the first edit lands before the third file you open beyond the ones named here; commit in stages; a stop for context is legitimate ONLY after the relay hook's own-window message (`RELAY_SUB_WARN`, quoted verbatim in the report) — never on your own estimate". The brief's measured anchors (`file:line`, counts, the decisions already taken) exist so the builder does not repeat the investigation; a builder that starts by reading is re-deriving them. A report with zero lines of code and "context exhausted" as the reason, without the hook message, violates the hard-rule-8 contract: the orchestrator does not resume the builder (hard rule 6) — it takes whatever `MEASURED` findings the report carries as anchors into a fresh brief that also says "start by writing". `POMIAR` (KonkretnyTMS batch 2.2, #802): builder-1 read ~15 files and stopped at 170,708 tokens — 17% of a 1M window, 17 calls, below the 45% hook threshold, no hook message — with no edit; builder-2 with the same findings in the brief and "start by writing" finished in 107 calls. The cost sat in the ordering, not in the task.
- The builder prompt is self-contained: task block, exact files, acceptance criteria, canon references for variant paths — and for every "copy pattern X" instruction **the latch that guards X** (the test that goes red when X is broken), with the requirement that the copy carries its own latch; `POMIAR` (batch 2.4, #580): the builder copied the mechanism without the per-tree test → P1 finding + one review round, "do NOT touch X" where relevant — and, when this orchestrator is itself a named subagent, its agent name with the instruction to deliver the final report via `SendMessage` to that name (see hard rule 7). When the orchestrator is the top-level session, subagent reports arrive as task-notifications on their own — do not ask for SendMessage to a name that does not exist.
- Discipline skills apply inside the builder: `test-driven-development` for new behavior, `systematic-debugging` on failures, `migration` when the diff changes a persisted or public shape (schema, data, API, config, dependency major) — the builder stops after the requested stage and never performs Contract implicitly.
- **Verification-type briefs are two-sided.** "Establish whether X or not-X, and name what decides it" — never "check whether X". A confirmation-shaped brief was measured (2026-08-29/30) to make a subagent confirm a false thesis while holding its disproof in its own context. Every subagent report labels load-bearing claims MEASURED (command / file:line) or INFERRED; the orchestrator treats an INFERRED link under a CONFIRMED claim as unverified.
- **A latch/test brief names its properties, and the report carries a MUTANT TABLE — one row per named property** (`property | mutant <sed> | expected RED | result | command`); a property without a row is SKIPPED and the report is incomplete. A builder proving a latch with mutants it picks itself picks the easiest — the branch that already works. `POMIAR` (batch 3.1, #730): the builder showed two RED mutants, both on the one working branch, and never mutated the brief's other requirements ("file composition of the frozen debt", "threshold per tree"); the reviewer's three control mutants found three vacuous branches, and the fixer cost 13.6M. Checklist the brief passes on for a latch: lists in a frozen baseline compared by content, thresholds per tree/unit, and every test has an input on which it can fail. **The mutant is EXECUTED, never narrated:** if the project's probe script (`scripts/mutation-probe.sh` or equivalent) does not fit the file after ONE attempt, the builder builds an ad-hoc harness — copy of the file + `--bootstrap` / `-d` / env override — and runs it; a row whose result is "would fail" without the quoted red output is not a row, and the report goes back. `POMIAR` (batch 3.2, #714): the builder spent most of 91 calls fitting the probe script to a cron entry point, then reported "MUTANT RED #2" as a conclusion; the reviewer had to execute the mutant itself.
- **The brief caps documentation in production code, says where the derivation goes, and names a template test.** "Docblock ≤ 10 lines in production code and on any single test method; the full derivation (the measured race, the counts behind a threshold, library line numbers, why the alternative fails, the mine for the next task) goes into the TEST FILE's header block — the class docblock or the docblock of the constant it explains — which has no line cap and in exchange carries only commands with their results, `file:line` anchors and named mines". **The cap is verified where it applies:** the longest run of added comment lines in `git diff <base>..<tip> -- <production trees>` (and, inside a test file, from the first `function` onward) — never the same awk over the whole diff, which measures the header the rule itself points at. `POMIAR` (KonkretnyTMS batches 4.7 and 4.8): two consecutive annexes recorded "the docblock cap did not hold" (24, then 40 lines) from the whole-diff form and proposed no change, while the production paths of both diffs took **0** added comment lines (`git show f84e92fc8 -- php`, `git show 6fc38710b -- php scripts`); an unscoped check turns a held rule into a standing violation report — and, when the task needs a test of a kind the repo already has once (a real library loaded in jsdom, a live-DB parity test, an A/B route test), the brief passes the path of that existing test as the template. `POMIAR` (batch 3.3, #697): a 38-line docblock on a 3-line function became a P3 and an inline cut; the builder's first-in-repo test loading real Bootstrap in jsdom cost ~79 calls to discover the CJS/`window.bootstrap` branch and the `FocusTrap` race — inherent once, ~60k avoidable on every repeat that gets the path.
- **A test against a live database asserts on rows it wrote itself, never on what the dev dump happens to contain.** The brief for such a test carries the rule as text: seed your own fixture (in a transaction with rollback, or with the project's run marker), assert on that fixture, and a `markTestSkipped` (or an early return) whose condition depends on the contents of the database is forbidden — a test that passes or does not exist depending on who last loaded the dump is a lottery, not a test. Skips stay legitimate only for infrastructure (host unreachable, missing opt-in variable). Projects that police this shape statically have a **test-corpus latch** — a test that scans `tests/` as text (a skip registry, a raw-PDO budget, an unconditional-skip scanner) — and it goes red from the builder's new file without ever referencing the builder's symbols, so the symbol-based targeted run of Step 2.4 cannot find it: the brief names those latches (`--filter '<A|B|C>'`, ≈ 2k tokens, under 10 s) and the builder runs them before the report whenever its diff adds, removes or changes a test file or a skip call. `POMIAR` (KonkretnyTMS batch 4.8, #516): the builder's live-DB test skipped on `purchase_invoices` being empty; the opus review (50 calls, 13 mutants) and the fixer both passed it, the end-of-batch full suite went red on `FixtureLotterySkipLatchTest`, and the repair (own row, transaction, rollback) was a 194k fixer spawn plus a second full-suite run — the whole +32% of that batch. Batch 4.7 had the same latch red for the opposite move (a removed skip), fixed inline for ≈10k; the class is cheap when caught by the builder and expensive when caught by the suite.
- **A decision with a documented precedent in the repo is the builder's to take, not to return.** When the standards, `incident-lessons`, a runbook or an existing migration already use the idiom (e.g. `SET FOREIGN_KEY_CHECKS=0/1` around an `ALTER` on a referenced column), the builder applies it and cites the precedent in its report; `ambiguous. ask:` is reserved for no precedent or conflicting ones. `POMIAR` (batch 3.1, #687): a builder stopped on exactly such a documented idiom; hard rule 6 forbade resuming it, so the stop cost a fresh spawn (~50k prefix) on top of the 19M already spent.
- **Every builder, fixer and verifier brief carries the "classifier-safe commands" block.** In auto mode the permission classifier bounces `cp` and `rm`, and a subagent that gets bounced improvises — measured to be worse than the bounce itself. The block: copies via `cat <file> > .claude/tmp/<name>` (a redirect, not `cp`); restore via `cat .claude/tmp/<name> > <file>` and confirm with `diff` (never `git checkout --`/`git restore` — the file may be shared, memory `zakaz-w-prompcie-to-nie-zapadka`); no `rm` outside `.claude/tmp/`; no `mv` of a tracked or generated artefact. `POMIAR` (batch 3.2, #714): two verifiers bounced on `cp`/`rm`, one switched to `mv` and a log artefact (`logs-report/latest.txt`) disappeared — 2–4 wasted calls per bounce, and a lost artefact on top.
- **Brief checklist — a rule from this step reaches the builder only as a line in the brief, never as a reference to this skill.** Before the spawn the orchestrator confirms the brief carries, as text: the task context block; the numbered items the report will walk as `DONE`/`SKIPPED`; the call budget; for every "copy pattern X" the latch of X; for a latch/test the property list; the docblock cap WITH its scope (production code and single test methods; the test file's header is where the derivation goes) and the template test path; for a live-DB test the own-fixture rule and the project's test-corpus latch filter; for a diff that adds or removes a route, controller method, endpoint or other counted artefact the project's counter-latch filter plus the ratchet-down-in-the-same-commit instruction; for a diff touching the source of a generated artefact the generator command plus the regenerate-in-the-same-commit instruction; for a Standard/Large builder the write-first line (first edit before the third unnamed file, staged commits, no self-declared context stop); the classifier-safe block; the report contract (hard rule 8) and the `SendMessage` target when one exists. A line the orchestrator cannot fill is written as `skipped: <reason>`, not left out. The same checklist governs a FIXER brief, plus the new-surface mutant rule of Step 2.2 — a fixer is a builder with a narrower task, not a builder exempt from proof. `POMIAR` (KonkretnyTMS batch 4.6): the docblock cap (added in 3.3) was in none of the batch's briefs and three new tests shipped 14-, 33- and 59-line docblocks; the batch's annex marked four rules "not applied", and every one of them was a rule absent from the brief, not a rule the subagent read and ignored.
- The builder returns, in the hard-rule-8 contract (terminal token first, `path:line` findings, no narration): **every numbered item of the brief with `DONE <path:line>` or `SKIPPED <reason>`** — an item absent from the report is treated as SKIPPED, and a SKIPPED item without a reason sends the report back. `POMIAR` (batch 2.4, #580): the builder silently dropped the probes the brief asked for; the omission was caught by the orchestrator's grep, not by the review — in #579 the same per-item requirement in the brief made the builder report it. Then: files changed, tests added/updated, verification commands it ran. Confirm with `git diff --stat` — a builder's success report is not evidence (`verification-before-completion`). **Every NUMBER from a subagent report that goes into the user-facing report, the ledger or the next brief is re-executed by the orchestrator first** — the report's command, run again, output quoted — or it is written as `reported, not re-measured`. A count from someone else's report, copied under a `MEASURED`/`POMIAR` label, passes every gate downstream because nothing else re-runs it. `POMIAR` (KonkretnyTMS batch 4.8): of three load-bearing `POMIAR` sentences in a writing subagent's report, one was false (`0 hits` where the real count was 2) and one incomplete (3 files against 5); two control commands at ≈ 0 tokens caught both, and the subagent's verdict was still correct — a wrong number in a right verdict is the one that survives review.

## Step 2: Review loop (cap 3)

1. Dispatch `code-reviewer` subagent on the diff:
   - the reviewer sizes itself from `git diff --stat` (its "Effort tier" table): **S** (≤ 3 files, < 100 lines) = seven axes, no risk plan, one pass, one-line coverage; **M** (≤ 10 files, ≤ 400 lines) = risk plan + coverage table; **L** = review units + a second pass per unit. The brief passes the stat, not a tier — a sensitive path (money/VAT/auth, migrations, CI, manifests) lifts the tier on the reviewer's side. Do not ask an S diff for "thorough" review: the extra process costs tokens and finds nothing the axes don't.
2. Split findings by severity:
   - **CRITICAL / HIGH / MEDIUM** → dispatch a **NEW** builder subagent (fresh context — never resume the builder that produced the diff; hard rule 6) with the task context block + the findings **verbatim** (file:line, description, suggested direction) + the reviewer's proposed diff when one was given + the proof required for each fix (which test/probe must turn RED→GREEN) + the current `git diff --stat` **+ the same mutant-table rule the builder brief carries, extended to the fixer's own new surface: every NEW guard, condition, branch or log line the fix introduces in production code gets a row (`line | mutant <sed> | expected RED | result | command`) with the red output quoted from an executed run, whether or not the finding named that line; a new line without a row = commit not ready for review, and the report goes back.** The fix-up prompt also says what the fixer must NOT do: no reading files outside the listed findings, no re-review of the untouched rest of the diff, no "while I'm here" changes — a fixer that re-explores the module pays the builder's cost a second time. **Before the re-reviewer is spawned, the orchestrator probes the fixer's new surface itself:** `git diff <previous tip>..HEAD -- <production paths> | grep '^+' | grep -E '<the project's guard/log spelling: if \(|Logger::|throw|return null>'` lists the new lines; each one is matched against the fixer's table, and a line without a RED row gets a one-command probe on a copy (`scripts/mutation-probe.sh` or the ad-hoc harness) — 2–5k tokens. A GREEN mutant goes back for a fix first (inline within the Step 2 bounds, else a fresh fixer), never to the reviewer: a reviewer that finds it charges a full round. `POMIAR` (KonkretnyTMS batch 8.5, #486): two of three review rounds were exactly this — fixer-1 added a `checkBalance` guard tested only for `status=0` (R2 found 4xx-with-body as P2), fixer-2 added a `Circuit OPEN` log line with no test (R3's mutant stayed GREEN); each round cost a review (117–143k) plus a fixer (205–253k) ≈ 350k, and the three probes G1 ran inline after R3 cost ≈ 2k each. The builder's table rule (Step 1) had held; the fixer briefs simply did not carry it. Then re-review the touched areas — the sign-off re-review is likewise a fresh reviewer fed the diff and the previous findings, not the previous reviewer resumed with its full exploration context.
   - **Trivial fix-up exception (inline, no fixer spawn):** when a finding's fix is test-only or docs-only, ≤ 40 lines, a copy of a neighbouring pattern already in the diff or the file, and provable by ONE command — a mutation probe for a test, `ls`/`git grep -nF` showing the corrected reference resolves for a doc — the orchestrator makes the edit itself (DIRECT, as in Step 0 Trivial) and quotes the probe's RED/GREEN line (or the resolving command) in the ledger/report. The probe copy of a TEST file keeps the file's directory depth (`.claude/tmp/<probe>/tests/<same subdirectories>/`): a test that resolves paths through `dirname(__DIR__, n)` goes red at the wrong depth for a reason unrelated to the mutant (`POMIAR` batch 2.5, one wasted call). The same exception covers a **LOW / P3 finding whose fix is ≤ 10 lines and changes no semantics** (a rename, a comment or docblock, assertion order, a message string) — a mutation probe is not required when the change touches no assertion and no branch; the orchestrator quotes the targeted test run instead. It also covers a **comment-only fix of any size up to 30 lines, in ANY file — production code, a migration header, a test docblock** — a diff in which no code token changes: proof is `git diff -w --stat` plus the language's syntax check on each touched file (`php -l`, `node --check`, `python -m py_compile`, or the migration runner's dry parse) plus the targeted run of the file's tests, and a mutation probe is NOT required because a comment has no behaviour to mutate. Two caveats: a comment latch, when the project has one (a docblock-cap scanner, a header-format test), runs with the targeted tests; and a comment edit in an ALREADY-APPLIED migration whose runner keys by file name changes nothing in any database — the orchestrator says so in the ledger instead of expecting a re-run. `POMIAR` (KonkretnyTMS batch 2.2, #802): three comment-only P3s (`php/config`, `sql/migrations`, a test docblock — 26 lines in 3 files) went to a fixer because the exception as written stopped at 10 lines and read as tests-only; the spawn cost 216k tokens, the same three edits inline cost ≈ 3k. And it covers a **P3 whose fix is ≤ 10 lines in production code or tests WITH semantics** (a missing `TRIM()`, an unlatched guard member, one added assertion) **only when the orchestrator itself executes a one-command mutation probe on a copy** and quotes RED under the mutant + GREEN restored + the targeted run — the probe is what makes a production-code edit admissible under hard rule 1, not the line count. `POMIAR` (batch 3.3): three such P3s (a `TRIM()` parity fix, one test for an unlatched guard member with its probe, a docblock cut) done inline for ≈ 8k total; batch 3.2 paid 140k + 175k for two fixer spawns of the same class — zero fixer spawns was the whole measured −18% of batch 3.3. `POMIAR` (batch 3.2): two cosmetic P3s in #735 went to a fresh fixer — 140k / 27 calls, most of them re-reading context — while a one-line test correction in #714 done inline cost ≈ 2k (`98782e004`); 70× for the same class of change. Anything outside those bounds (more than 10 lines of production code, a new mechanism, a semantic change without an executed probe) goes to a fresh fixer as above. `POMIAR` (batch 2.4): three such fix-ups done inline cost ≈ 25k tokens; the same three through fresh fixer subagents would have cost ≥ 300k. `POMIAR` (batch 2.5): six such fix-ups across three issues, each ≤ ~15 lines with the reviewer's `file:line` and proposed diff in hand, all inline — estimated ≥ 240k saved against six fixer spawns; `podagent-piszacy-tanszy-niz-inline` is about writing from scratch, not about a 10-line correction with the location already known. Hard rule 6 still forbids resuming the builder — the choice is inline or fresh, never resumed.
   - A finding the reviewer labels PLAUSIBLE (chain has an unmeasured link) is NOT dispatched as a fix — it goes back as a two-sided brief ("establish whether X or not-X") and only a MEASURED result enters the fix loop.
   - **LOW / stylistic / uncertain ("plausible")** → collect for the final report; never a fixer spawn for them. A LOW that meets the inline exception above may be done inline and reported as fixed; the rest are listed, not dropped.
5. **Test-only diffs (new latch, new fixtures, deleted assertions):** the reviewer's brief requires it to RE-RUN at least one of the builder's mutants AND one CONTROL mutant of its own choosing **placed on a step of the pattern the diff did NOT touch** (a sibling branch, the neighbouring tree, the untouched leg of the same guard) on its own copy of the file (never on the tracked file), and to report each as `mutant → RED/GREEN` with the command. Before its own mutants the reviewer checks the builder's mutant table against the brief's property list — a property without a RED row is a finding on its own. That report REPLACES Step 4 — there is no user-facing surface to verify, and a fresh verifier would repeat the same probe for a full spawn. A review of a test-only diff that only reads the assertions is a review of prose, not of a latch.
3. Repeat review→fix up to **2 iterations** for Standard tasks, **3 for Large** — 3 is the absolute ceiling (hard rule 2), 2 is where a Standard task stops even if findings remain. Cap exhausted → STOP; report remaining findings and why they persist. Never loop indefinitely, never merge review debt silently.
4. **Test-run economy inside the loop:** builders run TARGETED tests ONLY — a builder NEVER runs the full suite. **Targeted = the tests that reference the changed symbols, found by `git grep -l '<class or method>' tests/` across the WHOLE tests tree — never "the directory that mirrors the source" — PLUS, whenever the diff adds, removes or changes a test file or a skip call, the project's test-corpus latches (tests that read `tests/` as text: skip registries, budget latches, shape scanners), which reference no symbol and are therefore invisible to the grep — PLUS, whenever the diff adds or removes a route, a controller method, an endpoint, a permission entry, a raw SQL call site or any other artefact the project COUNTS, the project's counter latches (snapshot / budget / ratchet tests asserting an exact count of production artefacts — a route registry, a permission matrix, a raw-PDO budget, a DOM-tag budget): they read production code as text and assert `assertSame(<N>, …)`, so `git grep -l '<removed symbol>' tests/` returns 0 for them by construction, and a removal leaves them red until the constant is ratcheted DOWN in the same commit (an upward bump is never automatic — it is a design question the builder reports and the reviewer decides).** **PLUS, whenever the diff touches the SOURCE of a generated artefact** (a route inventory, an API listing, a schema dump, a permission-matrix document — a file a project script regenerates and a freshness latch compares to its source), the regenerated artefact in the same commit: the brief names the generator command (`php scripts/generate-<x>.php` or equivalent) and the latch's `--filter`; a pre-commit hook does not regenerate it, and the latch has no symbol to grep for. The orchestrator derives both latch lists once per project (the project's test rules or endpoint checklist, or `git grep -l 'ls-files\|glob(' tests/` and `git grep -lE 'BUDGET|Snapshot' tests/`) and puts the `--filter` into every builder and fixer brief. A behaviour change in a repository breaks mocks in service and controller tests; the mirror directory is where the change is least likely to be consumed. `POMIAR` (KonkretnyTMS batches 4.7 and 4.8): the same corpus latch went red at the full suite in two consecutive batches — once for a removed skip (≈10k inline), once for an added data-dependent skip (194k fixer + second suite run); neither builder, reviewer nor fixer ran it, because nothing in the diff pointed at it. `POMIAR` (KonkretnyTMS batch 2.2, #802): 26 route edits shipped without `scripts/generate-api-route-inventory.php`; `ApiRouteInventoryFreshnessLatchTest` was the single delta of the end-of-batch suite against the baseline (58 vs 57 names), a parity-check block and a closing commit. `POMIAR` (KonkretnyTMS batch 7.6, #408): the builder removed three CRUD routes and ratcheted the one counter latch the project's `CLAUDE.md` names (`WriteRoute*` 252→249); the two it does not name (`PermissionMatrixSnapshotTest` admin 29→26, `ControllerRawPdoBudgetLatchTest` 31→24 / BUDGET 447→440) went red only at the end-of-batch full suite — `git grep -c createGroup` on both files gave 0, an opus review had passed the diff — and cost a second full-suite run (≈15 min wall) plus a closing commit (≈20k). `POMIAR` (KonkretnyTMS batch 3.4, #688): the builder ran `tests/Repositories` for a change in `Repositories/`, eight mocks in `tests/Services` and `tests/Controllers` went red at the end-of-batch full suite, and the regression cycle (fixer + opus review over the >50-line threshold) cost ≈ 316k — the whole +14% of that batch. The FULL suite runs exactly once — at the final gate before the report, executed by the orchestrator or delegated to the reviewer alongside the final code review — and its result is reported with BOTH counts (passed AND skipped, with the skip reason). Re-running the full suite after every fix is waste, not rigor. On a shared dev database the full suite is a shared resource: when other lifecycles run in parallel, take the project's exclusive slot/lock for it (never run two full suites against one DB at once), and read the result from YOUR log path, not from "the newest log file" — a parallel run's log may be newer.

## Step 3: Security pass (conditional)

Trigger when the change touches: auth/session, input parsing, SQL, file upload/download, payments/money, secrets/config, permissions/groups, external API surface.
→ Dispatch `backend-security-coder` for a focused review of the touched paths. CRITICAL/HIGH findings feed back into the Step 2 fix loop (shares the same 3-iteration cap; if the cap is exhausted, security findings go to the user as blockers — security debt is never silently carried).

## Step 4: Verify (fresh subagent — anti-cheating gate)

Run the **`verify-e2e`** skill: fresh isolated subagent, adversarial prompt, evidence artifacts (screenshots / HTTP dumps / recordings). When the change lives in a worktree, the surface under test must be served FROM that worktree (per-worktree server port), and the verifier must show a **discriminator** — an observation that differs between the fixed tree and the unfixed one — because a server that answers on some port proves only that a server is up, not which tree executes.

The verify brief is the `verify-e2e` Step 3 template with EVERY line filled — a measurement from this turn or `skipped: <reason>`. The `Entry point` line carries the orchestrator's own grep of the handler binding, so an unreachable GUI path is scoped out before the spawn instead of being diagnosed by the verifier. `POMIAR` (KonkretnyTMS batch 4.6, #549): the grep showing "no button" sat in the orchestrator's exec row; the brief did not carry it, and ≈150k of a 190k verify went to two pre-existing blockers on the unreachable path.

- **PASS** → proceed to report with evidence paths.
- **FAIL** → repro steps go to a builder subagent; re-verify with a NEW fresh verifier. Cap 3 verify-fix cycles.
- **BLOCKED** (missing env: account, key, tool) → record the gap in `docs/VERIFICATION_ENV.md`, mark the task "verified: NO (blocked on X)" in the report. A blocked verification is a first-class result, not a footnote.

## Step 5: Report package

The ONLY thing the user needs to read. Structure:

```
## <Task title> — ready for review
**What changed & why:** 2-4 sentences.
**Branch / commits:** agent/<slug>, tip SHA, N commits, diff stat (the SHA is what the user merges — without it the report is not actionable).
**Review:** X iteration(s); fixed: <counts by severity>; remaining (not auto-fixed): <LOW/uncertain list or "none">.
**Security pass:** run/skipped (+why) ; findings summary.
**Verification:** PASS/FAIL/BLOCKED + evidence paths (screenshots/recording/responses).
**Open items / blockers:** anything needing a human decision.
**Your move:** e.g. "review evidence → merge PR" / "provide X to unblock verification".
```

Never merge, push to the deploy branch, or deploy — present the package and stop. If the project uses a done-label on the tracker (e.g. "to be merged"), add it to the issue at this point — it is the only tracker write allowed, and without it the next wave re-triages the issue from scratch.

## Hard rules

1. **Orchestrator writes no code.** Every implementation and fix goes through a subagent (the only exceptions: trivial DIRECT edits from Step 0 and the Step 2 inline fix-up bounds — ≤ 10 lines with an executed probe, or a comment-only diff ≤ 30 lines with `git diff -w --stat` + syntax check).
2. **Caps are absolute:** review-fix iterations 2 (Standard) / 3 (Large) — never more than 3; verify-fix cycles 3. Exhausted cap → stop and report, never widen scope to "make it pass".
3. **Fresh context for verification.** The verifier never shares context with any builder.
4. **Evidence or it didn't happen** — `verification-before-completion` governs every claim in the report.
5. **Manual step spotted twice → automate it.** If the user has to correct or remind you about a step of this lifecycle, propose adding it to this skill / project CLAUDE.md immediately. **And the same rule reported as broken a third time is a defect in the rule, not in the agent** — before writing "instance of an existing rule, not a gap" again, check what the verdict actually measured against what the rule says (`retro` Step 2), then change the rule's mechanism: its scope, its check command, or a probe that runs in the pipeline. `POMIAR` (KonkretnyTMS batches 3.3, 4.6, 4.7, 4.8): the docblock cap was recorded as broken in four annexes, escalating 24 → 40 lines, each time filed as an instance of an existing rule; the rule had been added to ten agent overlays and every brief, and the last two verdicts were measuring the test-file header that the rule itself designates as the destination.
6. **One agent per unit of work — a finished agent is never resumed for the next unit.** Build, each review-fix iteration, each re-review, each security re-check and each verify run is its own fresh subagent whose prompt carries the task context block, the previous findings and the current diff state; the report of the previous agent is the compression point (200k of exploration → 2k of findings), so resuming carries ballast instead of trimming it. MEASURED (2026-09-13, batch of 5 issues, 32 subagents, 503M cache-read tokens): the builder resumed for three review iterations cost 94M input tokens over 497 turns and finally overflowed its context mid-iteration; the fresh builder spawned to finish that same iteration did more work for 24M. Resuming a 240k-context reviewer for a 15-tool-call sign-off cost ~25M; a fresh diff-only reviewer would cost ~3M. A resumed agent pays its whole accumulated context on every turn.
7. **Every subagent reports by `SendMessage` to the orchestrator BY NAME.** Spawn subagents with an explicit `name:`, put the orchestrator's own agent name in their prompt, and require the final report to be sent to it. MEASURED (same batch): task-notifications of subagents spawned by a nested orchestrator landed with the top-level session, not the spawner — every builder report had to be relayed by hand, doubling the reading and stalling one issue for 3 h. Agents whose `tools:` list is restricted must include `SendMessage`. Spawn every subagent with an explicit `model:` as well (project policy: writers `sonnet`, reviewers `opus`) — the agent registry loads at session start and can be stale. Exception: when the orchestrator is the top-level session (no agent name), reports arrive as task-notifications and no SendMessage target is given.
8. **Subagent reports are findings, not stories — and their first token is a verdict.** Put the report contract into every subagent prompt: (a) the first line is one terminal token the orchestrator can grep — builder: `done.` / `too-big. split: <n one-line tasks>` / `ambiguous. ask: <one question>` (no repo precedent — Step 1) / `needs-confirm. op: <command>` / `regressed. revert <path:line>. cause: <fragment>`; reviewer: `No issues.` or the verdict line; verifier: `VERDICT: PASS | FAIL | BLOCKED`; (b) every finding is `path:line` first, symbols backticked, MEASURED/INFERRED labelled, every COUNT carries the command that produced it in the same sentence and every `0` carries its positive control (the same pattern against a line known to match), a number taken from the brief or another agent is written as `reported: <source>`, and a builder's report walks the brief's numbered items as `DONE <path:line>` / `SKIPPED <reason>` (Step 1); (c) no narration of tool calls, no exploration story, no restating the brief — the diff is the artifact, the report is the proof; (d) no invented abbreviations (`cfg`, `impl`, `req`, `res`, `fn`, `auth`) and no arrow chains (`→`) in prose — the tokenizer splits them like the full word, so they save nothing and cost the reader a decode; plain words, exact names. Security warnings and irreversible-action confirmations are written in full sentences regardless. A report that violates (a) or (b) is sent back for the contract, not read around.
